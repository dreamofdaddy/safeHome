## 2026-10-21 사용자 확정 정책: 재시도 3회·호수 기반 층 추정

검증: Integration JUnit 24개·코어 105개, Backend 관련 6개, Frontend 41개·lint·배포 빌드 및 JAR 빌드 통과. 실제 공공 API·OpenAI는 이번 정책 변경 검증에서 호출하지 않았다.

이 절은 앞서 기록된 최대 1회 재시도 및 호수로 층을 추정하지 않는 정책을 대체한다. 과거 검증 기록은 당시 결과로 보존한다.

- 일시적 HTTP 502/503/504·통신 오류·빈 응답·일반 XML 구문 실패는 최초 호출 후 최대 3회 재시도한다(페이지당 최대 4회). 간격은 300/600/900ms이며 기존 전체 120초 예산·속도·페이지·응답 크기 제한을 유지하므로 남은 예산에 따라 일찍 중단할 수 있다.
- 인증/권한 오류, 금지된 DOCTYPE, 크기 초과, 입력·페이징 오류는 반복 호출로 해결하지 않는다. 실패·부분 수집을 확정 결과로 바꾸지 않는다.
- 공급기관의 유효한 층번호가 없고 지상 구분이 명확한 경우, 정규화된 3~5자리 숫자 호수에서 마지막 두 자리를 제외한 숫자를 층으로 추정한다. 예: 202호→2층, 1203호→12층. 끝 두 자리가 00인 호수, 문자·복합 호수와 지하/구분 불명은 이 규칙으로 추정하지 않는다.
- 명시된 공급기관 층번호를 우선하고 기존 지번·동·호·건물 관리번호 관계·유일성 검사는 유지한다. 추정 층과 요청 또는 호명칭의 명시적 층이 다르면 FLOOR_INFERENCE_CONFLICT / UNVERIFIABLE이다. 추정 불일치만으로 NOT_FOUND를 선언하지 않는다.
- 추정에 따른 일치 또는 중복 후보에는 FLOOR_INFERRED_FROM_UNIT_NUMBER를 reason에 저장·전달한다. 공급기관 원문과 원래 null인 층 필드는 덮어쓰지 않는다. 화면에서 추정 기반 결과임과 원본 확인 필요를 안내한다. 위험 점수·등급은 바꾸지 않는다.
- 본인 매물의 CALL_FAILED와 COMPLETED/UNVERIFIABLE/CANDIDATE_FLOOR_NUMBER_UNAVAILABLE에서 새 이력으로 재검증할 수 있다. 최신 PARSED 문서·스냅샷, 동시 중복 제한과 소유자 검사를 유지한다. 이전 이력은 보존하고 등기부 재판독·안전성 재분석은 실행하지 않는다.
- DB 열·응답 필드 추가는 없으며 기존 reason으로 근거를 보존한다. 변경 전 저장 결과는 자동으로 새 정책의 결과로 바꾸지 않는다.

# 건축물 식별 자동 연계

## 실행 경계

등기부 판독 결과·스냅샷을 저장하는 트랜잭션에서 `building_identifications` 기록을 만들고
`listings.current_building_identification_id`를 새 기록으로 바꾼다. 주소 검색의 확정 지번과
명시적 동·층·호가 충분하면 `PENDING`, 부족하거나 충돌하면 `INPUT_INCOMPLETE` 또는
`INPUT_CONFLICT`, 기능이 꺼져 있으면 `DISABLED`로 남긴다. 실제 Integration Server 호출은
판독 트랜잭션의 `afterCommit` 이후 별도 실행기에서만 시작한다.
각 기록에는 당시 매물 주소·상세주소·검색 근거, 판독한 동·층·호의 원문·정규화 값과
구성된 요청을 함께 보관한다.

주소 또는 상세주소·검색 근거가 변경되면 현재 포인터를 비운다. 새 등기부 스냅샷이
확정되면 새 기록을 만들고 포인터를 바꾼다. 이전 기록은 삭제하지 않는다. 작업자의
최종 저장은 포인터가 여전히 자기 기록을 가리키는 경우에만 `COMPLETED` 또는
`CALL_FAILED`가 된다. 그 사이 포인터가 바뀌면 이전 기록은 `SUPERSEDED`로 남고
새 기록의 최신 상태를 덮어쓰지 않는다.

## 상태와 표시

| 실행 상태 | 식별 결과 | 의미 |
|---|---|---|
| `NOT_REQUESTED` | 없음 | 현재 기록 없음 |
| `PENDING`, `RUNNING` | 없음 | 대기·조회 중 |
| `INPUT_INCOMPLETE` | 없음 | 확정 지번 또는 명시적 층·호 등 부족 |
| `INPUT_CONFLICT` | 없음 | 원문 출처 간 동·층·호 또는 주소 근거 충돌 |
| `DISABLED` | 없음 | 기능 비활성화 |
| `CALL_FAILED` | 없음 | 내부 호출·공급기관 호출 실패 또는 응답 계약 오류 |
| `COMPLETED` | `MATCHED`, `NOT_FOUND`, `AMBIGUOUS`, `UNVERIFIABLE` | 완료된 식별 결과 |
| `SUPERSEDED` | 있을 수 있음 | 최신성 무효화된 이전 기록 |

`PARENT_NOT_CORROBORATED`는 완료된 조회의 `UNVERIFIABLE`이다. 공급기관 장애,
시간 초과, 인증 실패, 내부 호출 장애 등 불완전한 호출은 `CALL_FAILED`로 기록한다.
`NOT_FOUND`를 안전 판정으로 해석하지 않는다. 건축물 식별 상태는 별도 매물 상세 API와
화면에 표시하며 위험 점수·등급·위험 요소 계산에 입력하지 않는다.

조회가 모두 완료됐지만 대상 전유부의 층번호만 확인할 수 없는 경우는
`COMPLETED / UNVERIFIABLE / CANDIDATE_FLOOR_NUMBER_UNAVAILABLE`이다.
공급기관의 `flrNo=0`을 유효한 층으로 해석하거나 호수로 층을 추정하지 않는다.
2026-10-21 검증 DB의 매물 3을 기존 저장 요청으로 재실행해 이 상태를 확인했으며,
기존 실패 이력은 남기고 새 이력만 현재 포인터로 연결했다. PDF 판독은 다시 실행하지 않았다.

## 재시작과 재시도

작업 기록은 외부 호출 전에 DB에 커밋되므로 재시작으로 실행기가 중단되어도 남는다.
기동 시 현재 포인터에서 벗어난 대기·진행 기록은 `SUPERSEDED`로 정리한다. 기능이
활성화되어 있으면 `PENDING`과 중단된 `RUNNING`을 다시 실행하되, 한 기록당 외부
호출 시도는 최대 2회다. 2회에 도달한 중단 작업은 `CALL_FAILED`로 종료한다.
이미 `CALL_FAILED`인 공급기관 장애는 재시작만으로 자동 반복하지 않는다. 기능이
꺼진 상태로 기동하면 남은 대기·진행 기록을 `DISABLED`로 두고 호출하지 않는다.
다시 활성화해 기동하면 현재 기록 중 남은 시도가 있는 `DISABLED` 작업을 재개한다.

현재 복구 정책은 로컬 단일 Backend 인스턴스를 기준으로 한다. 다중 인스턴스 운영에는
작업 소유권 임대와 분산 호출량 제한이 필요하다. 실행기 큐가 가득 차서 커밋 이후
즉시 제출하지 못한 `PENDING` 작업은 다음 기동에서 복구한다.

## 로컬 실호출 검증

## 2026-10-21 외부 호출 이력 연결

Backend 작업자는 식별 이력 번호를 `X-SafeHome-Identification-Id`로 전달한다.
Integration Server는 작업 UUID를 생성하고 날짜별 외부 호출 이력의 `job.identificationId`에 번호를 저장한다.
REST 응답 헤더 `X-SafeHome-Integration-Job-Id`에 작업 UUID가 있으며 응답 본문과 DB 구조는 유지한다.
Backend 이력의 재시도는 같은 식별 번호·새 UUID로 구분할 수 있다. MCP/직접 호출은 식별 번호가 없을 수 있다.
로컬 기록은 저장소 밖 `D:/safehome-data/integration/call-history`에 보관하며 실패 시 식별/위험 결과를 바꾸지 않는다.
소급 이력은 만들지 않는다. 기존 실제 매물은 재실행하지 않았고 합성 테스트와 기존 결과 조회로 연결 변경을 검증했다.
# 조회 실패 후 사용자 재시도 (2026-10-21)

## 2026-10-21 식별 재시도와 추정 성공 안내 정리

- 재시도 버튼 이름은 '건축물 식별 재시도'로 통일한다. CALL_FAILED 및 COMPLETED의 UNVERIFIABLE·AMBIGUOUS·NOT_FOUND에 제공하며 층 추정 충돌도 포함한다. MATCHED·진행 중·입력 부족/충돌에는 제공하지 않는다.
- Backend도 같은 완료 상태를 재시도 대상으로 허용한다. 기존 소유자·최신 PARSED 문서/스냅샷·중복 방지·이력 보존 조건은 유지한다.
- 호수 추정으로 MATCHED이고 reason이 FLOOR_INFERRED_FROM_UNIT_NUMBER인 경우만 노란 박스에 '호수로 추정한 층을 적용해 일치하는 호를 확인했습니다.' 한 문장을 표시한다. 종전 장문과 중복 본문 문구를 제거한다. 명시적 층 일치·추정 중복 후보에는 추정 성공 문구를 표시하지 않는다.

### 2026-10-26 다운로드 배치 및 공공 API 수동 재조회

- 등기사항증명서 PDF 다운로드를 건축물대장처럼 파일명 오른쪽에 배치한다.
- 공공 API 조회 버튼을 상시 표시하고 식별 성공(MATCHED) 후에도 수동 재조회를 허용한다. 진행 중 요청, 비활성 연계, 유효한 최신 등기사항증명서·주소 근거가 없는 요청은 기존처럼 차단한다. 각 조회는 새 이력을 만들며 이전 이력과 등기사항증명서·위험 분석은 보존한다.
- 최신 건축물대장 PDF가 분석 완료·유효·필수 문서 충족 상태이면 공공 API 영역에 '건축물대장 문서 분석이 완료되어 추가 조회는 선택사항입니다.'를 표시한다. 오래된 자료·실패·필수 문서 누락에는 표시하지 않는다. 문서 분석 완료를 법적 안전 확정으로 표현하지 않는다. 실제 공공 API·AI는 자동 호출하지 않는다.
- 실제 57번의 저장된 API 상태는 DISABLED였고 로컬 연계 활성 설정이 빠져 있었다. 공유 설정의 인증값은 보존한 채 integration.enabled=true를 추가했다. 이전 DISABLED 이력은 재시작으로 자동 재개하지 않으며 유효한 최신 자료를 갖춘 소유자의 수동 조회로 새 이력을 만든다. PENDING/RUNNING의 기존 장애 복구는 유지한다.
### 2026-10-26 문서 분석과 독립적인 공공 API 조회

- 수동 조회는 등기사항증명서·건축물대장 PDF의 등록/분석 여부와 관계없이 실행한다. POST /api/listings/{id}/building-identification/lookup 는 선택적 JSON {addressSearchEvidence, detailAddress}를 받는다. 생략한 값은 매물 등록 정보를 사용한다. 기존 /retry 경로는 과거 문서 기반 요청과의 호환성을 위해 유지한다.
- 주소검색 근거가 없는 기존 매물은 공공 API 카드의 조회 주소검색에서 등록 주소와 동일한 주소를 선택하고 조회용 상세주소에 동·지상/지하·층·호를 보완한다. 임의의 다른 주소로 조회하지 않도록 서버에서도 기존 주소와 일치를 검사한다. 조회용 보완값은 매물 원본을 수정하지 않으며 해당 요청의 비공개 input_json에 보존한다. 명시적인 층·호가 부족하면 INPUT_INCOMPLETE로 안내하고 외부 API를 호출하지 않는다.
- V25는 API 조회 이력의 registry_snapshot_id·registry_document_id를 nullable로 변경한다. 독립 조회는 두 참조를 null로 저장하고 input_json의 queryBasis=LISTING으로 출처를 구분한다. 기존 문서 기반 이력의 참조는 그대로 보존한다. 수동 조회 결과는 등록/보완 정보 기준 호실 식별이며 등기사항증명서와의 동일성을 확인했다는 뜻이 아니다.
- 매물 소유권·연계 활성 상태·진행 중 중복 검사는 유지한다. 새 이력을 현재 결과로 지정한 뒤 커밋 후 비동기 조회하며 예전 작업은 현재 결과를 덮지 않는다. 최신 문서가 실패했거나 문서가 없더라도 독립 조회가 가능하다. 기존 문서·스냅샷·위험 분석은 변경하지 않는다. 유료 AI·문서 자동 분석은 실행하지 않는다.
- 운영 전환 시 조회용 주소 근거·상세주소 스냅샷도 기존 민감정보 보존/삭제·백업·접근 제어 정책에 포함한다.
### 2026-10-26 공공 API는 사용자 수동 조회로만 실행

- 등기사항증명서 분석 완료 시 DocumentAnalysisPersistenceService에서 BuildingIdentificationService.prepare를 호출하던 연결과 prepare의 자동 작업 예약을 제거했다. 분석 성공은 등기 문서·소유자·권리·스냅샷 저장까지만 수행하고, 공공 API 조회 이력이나 외부 요청을 생성하지 않는다. 건축물대장 PDF 분석도 외부 API를 자동 호출하지 않는다.
- 건축물대장 조회 버튼의 인증된 POST /building-identification/lookup 또는 명시적 /retry 요청으로만 API 작업을 시작한다. 이전 수동 조회의 유효한 저장 입력도 재시도할 수 있다. 등기사항증명서의 분석/재분석·조회 화면 열기·상태 새로고침은 API 호출을 시작하지 않는다.
- 서버 시작 시 PENDING/RUNNING 작업을 외부 호출로 자동 재개하지 않고 CALL_FAILED / REQUEST_INTERRUPTED로 표시한다. 다시 조회하려면 사용자가 조회 버튼을 눌러야 한다. 기존 완료·실패·비활성 결과와 문서/위험 분석 이력은 유지한다. 하나의 수동 요청 안에서 Integration Server가 수행하는 기존 제한적 일시 오류 재시도 정책은 유지한다.
- DB migration·공유 설정·Frontend 계약 변경은 없다. 앞선 문서의 판독 커밋 후 자동 연계·재시작 자동 재개 기록은 이 결정으로 대체한다. 검증에는 합성 PDF와 모의 외부 Client를 사용하며 실제 AI/공공 API를 호출하지 않는다.

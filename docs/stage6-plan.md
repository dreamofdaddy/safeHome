## 설계 보완 사항

- Integration Server는 공공데이터 식별 근거만 반환한다. 위험 판단과 점수는 Backend가 담당한다.
- 건축물대장 관리번호와 등기부 고유번호는 다른 식별자로 유지한다.
- 전유부 응답에는 상위 PK가 없다. 동일한 `mgmBldrgstPk`의 기본개요에서
  `mgmUpBldrgstPk`를 읽어 표제부 PK와 정확히 대조한다. 관계를 추정하지 않는다.
- `hoNm`의 층 표시가 `flrGbCd` 또는 `flrNo`와 충돌하면 UNVERIFIABLE로 처리한다.
- 정상 응답은 기존 Backend ApiResponse 구조를 따른다.
- MATCHED의 후보는 정확히 1개, NOT_FOUND는 0개, AMBIGUOUS는 2개 이상이다.
- 불완전 수집, 해석할 수 없는 잠재 후보, 부모 관계 미확인은 UNVERIFIABLE이다.
- 전체 페이지 수집을 마쳐도 공급기관이 조회 중 데이터를 바꾸는 상황의 완전한 스냅샷은 보장되지 않는다.
  총건수·ID 중복 검사를 넘어선 스냅샷 일관성은 공급기관 한계로 기록한다.
- 초기 자동 연계 선행조건이었던 주소 검색 근거 보존과 동·층·호 입력 생성기를 적용했다.
  값이 부족하거나 서로 충돌하면 외부 호출을 하지 않고 별도 입력 상태로 기록한다.
- 별도 건축물 식별 이력 테이블에 요청·입력 근거와 실행 상태·결과를 저장한다.
  기존 properties의 등기부 고유번호를 대체하지 않는다.
- Redis 캐시 도입은 원문 명세·실제 조회 검증 후 진행한다.
  완전 수집 원천 묶음과 실제 queriedAt만 캐시하며 실패·부분수집은 제외한다.
- 호출 이력에는 작업 ID, API명, 페이지, 성공/오류 분류, 지연시간을 저장한다.
  키·전체 URL·응답 원문은 저장하지 않는다. 현재 지속 이력 저장은 미구현이다.
- 120초 전체 수집 예산과 페이지 100건은 초기값이다.
  아파트 실제 부하·할당량에 따라 조정하고 운영 분산 호출량 제한을 추가한다.

## 후속 실행 순서

1. 주소 검색 근거·입력 생성기와 실행 상태·식별 결과의 별도 저장 모델을 적용했다.
   판독 커밋 이후 외부 조회, 오래된 비동기 응답 차단과 매물 상세 표시·재시작 복구는
   `docs/building-identification-flow.md`에 기록했다.
2. MCP의 잘못된 요청 응답에서 내부 스택 정보가 노출되지 않도록 제한한다.
3. Redis 캐시·호출 이력·분산 호출량 제한은 운영 요구와 실측 부하를 반영해 구현한다.
4. 로컬 1차 개발 완료 범위와 검증 한계는 아래 판정을 따른다. 운영 전환 과제는 별도로 수행한다.

## 2026-10-21 화면 검증 및 1차 완료 판정

개발 6단계의 로컬 단일 Backend 기준 1차 개발 범위는 완료했다. 독립 서버·REST/MCP,
전체 수집과 보수적 식별, 주소 근거·입력 생성, 판독 커밋 이후 비동기 연계,
별도 이력 저장·최신성 차단·제한적 재시도·재시작 복구 및 상세 화면을 포함한다.
이는 공개 운영 전환 완료 판정과 다르며, 아래 운영 과제를 완료한 뒤 운영 전환을 판단한다.

### 이번 확인과 유지한 결과

- 전용 Frontend `http://127.0.0.1:5174`의 `/api`를 검증 Backend `8180`으로 연결했다.
  실행은 `frontend`에서 `npm run dev -- --config vite.stage6.verify.config.ts`를 사용한다.
  일반 개발 연결 `5173 → 8080`과 구분하며 실제 설정·인증된 상세 API·브라우저를 확인했다.
- 검증 DB는 `safehome_stage6_real_pdf_test`, Integration Server는 최신 JAR의 `8090`이다.
  매물 3의 현재 포인터는 새 이력 2번이며 `COMPLETED / UNVERIFIABLE`이다.
  기존 이력 1번의 `CALL_FAILED / MALFORMED_RESPONSE`는 보존했다.
- 브라우저에서 “건축물대장 조회 완료”, “공급기관 층 정보 부족으로 확인 불가”를 확인했다.
  이전 조회 실패 문구와 내부 사유 코드는 표시되지 않는다. 위험 점수·등급과 별도 영역이다.
- 기존 `PARSED / OPENAI`와 스냅샷 1번을 유지했고 OpenAI 재판독은 실행하지 않았다.
  이 실제 매물에는 저장된 위험 분석 결과가 없어 해당 결과의 보존은 실데이터 화면에서 검증하지 못했다.
  기존 Backend 장애 경로 검사와 Frontend의 실패·식별 불가 회귀 검사에서 판독 및 위험 결과 유지를 확인했다.
- Frontend `npm run check`: 6개 파일, 36개 검사 및 TypeScript·배포 빌드 통과.
  적용 후 최종 lint도 통과했다. 기존 Integration Server `test coreTest bootJar`와 코어 105개
  통과 결과를 재사용했으며 이번 화면 수정으로 외부 API를 다시 조회하지 않았다.
  검증용 임시 인증 세션·부트스트랩은 폐기했다. 실제 키·문서 원문은 저장소에 추가하지 않는다.

### 검증 한계

- 공급기관의 대상 전유부 `flrNo=0`은 유효한 층번호가 아니다. 호수에서 층을 추정하지 않으며
  `CANDIDATE_FLOOR_NUMBER_UNAVAILABLE`을 `MATCHED` 또는 `NOT_FOUND`로 변경하지 않는다.
- 과거 `MALFORMED_RESPONSE`는 같은 저장 요청에서 재현되지 않았다. 당시 응답이 없어 정확한 원인은 미확정이다.
  현재 진단 패치는 향후 오류의 API·페이지·파싱 단계만 남기며 응답 원문·키·전체 URL은 남기지 않는다.
- 빌라·아파트의 기존 MATCHED 실호출 증빙은 당시 응답에 대한 검증이다. 공급기관 데이터의
  지속적인 정확성이나 모든 건물 유형의 식별 성공을 보장하지 않는다.

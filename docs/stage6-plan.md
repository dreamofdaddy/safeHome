## 설계 보완 사항

- Integration Server는 공공데이터 식별 근거만 반환한다. 위험 판단과 점수는 Backend가 담당한다.
- 건축물대장 관리번호와 등기부 고유번호는 다른 식별자로 유지한다.
- 전유부 응답에는 상위 PK가 없다. 동일한 `mgmBldrgstPk`의 기본개요에서
  `mgmUpBldrgstPk`를 읽어 표제부 PK와 정확히 대조한다. 관계를 추정하지 않는다.
- `hoNm`의 층 표시가 `flrGbCd` 또는 `flrNo`와 충돌하면 UNVERIFIABLE로 처리한다.
- 정상 응답은 기존 Backend ApiResponse 구조를 따른다.
- MATCHED의 후보는 정확히 1개, NOT_FOUND는 0개, AMBIGUOUS는 2개 이상이다.
- 불완전 수집, 해석할 수 없는 잠재 후보, 부모 관계 미확인은 UNVERIFIABLE이다.
- 전체 페이지 수집을 마쳐도 공급기관이 조회 중 데이터를 바꾸는 상황의 완전한 스냅샷은 보장되지 않는다.
  총건수·ID 중복 검사를 넘어선 스냅샷 일관성은 공급기관 한계로 기록한다.
- Backend 등기 판독 DTO에 시군구·법정동 코드와 지상/지하 값이 없다.
  주소 검색의 구조화 정보 보존과 판독 결과의 동·층·호 구조화가 자동 연계 선행조건이다.
- 데이터 소스 저장은 후속 스키마 설계에서 별도 건축물대장 근거 테이블로 관리한다.
  기존 properties의 등기부 고유번호를 대체하지 않는다.
- Redis 캐시 도입은 원문 명세·실제 조회 검증 후 진행한다.
  완전 수집 원천 묶음과 실제 queriedAt만 캐시하며 실패·부분수집은 제외한다.
- 호출 이력에는 작업 ID, API명, 페이지, 성공/오류 분류, 지연시간을 저장한다.
  키·전체 URL·응답 원문은 저장하지 않는다. 현재 지속 이력 저장은 미구현이다.
- 120초 전체 수집 예산과 페이지 100건은 초기값이다.
  아파트 실제 부하·할당량에 따라 조정하고 운영 분산 호출량 제한을 추가한다.

4. 지상 1층과 지하 1층 구분, 전각·제·선행 0 정규화, 호명칭 원문 보존
5. 빈 결과의 완전 수집만 NOT_FOUND
6. 마지막 페이지 실패·건수 변경·중복 페이지·알 수 없는 필드: UNVERIFIABLE

8. REST/MCP 동일 입력의 결과 일치, 인증 없이 외부 도구 호출 차단
9. Backend 미기동·Integration 장애 시 기존 위험분석 점수 변경 없음
10. 캐시 도입 시 TTL·원조회시각·부분결과 미캐시·장애 복구

## 후속 실행 순서

1. 주소 검색 근거·입력 생성기와 실행 상태·식별 결과의 별도 저장 모델을 적용했다.
   판독 커밋 이후 외부 조회, 오래된 비동기 응답 차단과 매물 상세 표시·재시작 복구는
   `docs/building-identification-flow.md`에 기록했다.
2. MCP의 잘못된 요청 응답에서 내부 스택 정보가 노출되지 않도록 제한한다.
3. Redis 캐시·호출 이력·분산 호출량 제한은 운영 요구와 실측 부하를 반영해 구현한다.
4. 전체 사용자 흐름과 장애 경로를 검증한 뒤 개발 6단계 완료 여부를 판정한다.
